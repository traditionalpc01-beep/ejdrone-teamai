# ejdrone-share：把个人踩坑变成团队经验

一条经验只有被提交进团队仓库并通过评审，才会变成团队的知识。这条技能规定两件事：
**什么时候值得总结**，以及**什么时候才允许真的提交**。

## 你不需要懂 git

`ejdrone contribute` 一条命令包办提交的全部手续：自动建分支、自动提交、自动开合并请求（MR）。
你不用学 git，也不用懂分支和合并是什么。你唯一要做的，是把命令输出里的合并请求链接发给
管理员（或在群里 @管理员），等评审合入——合入后全团队下次开会话自动拿到这条经验。

## 什么算一条 learning

- 用户反复纠正你做同一件事（说明团队约定和你的默认预期不一致）。
- 同一个工具/命令连续失败，最后找到原因并解决（下次别人还会踩）。
- 线上问题的排查路径：现象 → 误判 → 真因 → 修法，值得按时间线复述的。

不值得提交的：一次性事故细节、含密钥或内部账号配置的内容、只对你本机成立的环境差异。

## 怎么做

1. 写一份 markdown 到成员本地（任意临时路径，例如 `~/learning-draft.md`），结构建议：
   背景/现象 → 解决过程 → 结论（下次怎么做）。开头写或让工具补 frontmatter：
   `title`（一句话主题）、`date`（YYYY-MM-DD）、`tags`（2–5 个，方便 recall 命中；缺了不会被拒，评审会提醒补）。
2. **先预览，再确认，最后提交**。先给用户看落库形态：

   ```bash
   ejdrone contribute --file ~/learning-draft.md --title "Kafka 消费积压复盘" --dry-run
   ```

   `--dry-run` 只打印将要写入仓库的文件内容与目标路径，不建分支、不开 MR。
3. 用户看过预览并**明确说"分享给团队"**之后，才去掉 `--dry-run` 真正执行：

   ```bash
   ejdrone contribute --file ~/learning-draft.md --title "Kafka 消费积压复盘"
   ```

   角色订阅了多个 namespace 时加 `--ns <namespace>`；缺省按 push 的同一条规则映射角色。
   命令会自动建分支并提交，输出里给出合并请求（MR）链接；把它发给管理员评审，
   合入后全团队下次开会话自动拿到。
   本机没装 git 也可能直接提交：管理员配了 Codeup 免 git 推送（Codeup 仓库 + 环境变量
   `EJDRONE_CODEUP_TOKEN`）时，命令会自动走 API 推送——视管理员配置而定，不确定就先跑一次看提示。
   没走通时命令会给出明确指引，此时把草稿文件直接发给管理员代提交也是正规通道
   （管理员侧跑同一条 contribute 命令）。
4. 命令提示"目标路径已存在"时：不要改名硬绕，把已存在那份的标题路径报给用户，让 TA 决定
   是换标题另写一条，还是那件事已经记录过、这次该在原文上补充（补充走 MR 直接改仓库文件）。

## 边界（必须遵守）

- **没有用户明确同意，绝不执行真正的 contribute**。默认只到第 2 步（总结 + dry-run 预览 + 询问）。
- 不要直接改 `~/.ejdrone/knowledge/` 镜像里的文件来"补充团队经验"——那是投递产物，团队拿不到；
  新经验只走 `ejdrone contribute`。
- learning 里不写密钥、token、内部凭据（评审也会兜底，但不要依赖评审）。
- `ejdrone-share` 与 `ejdrone-recall` 是内置技能名，不要把它们（或改名的副本）push 回团队仓库。
