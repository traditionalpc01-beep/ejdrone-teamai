# AI 委托安装（第三通道：把安装交给成员自己的 AI 工具）

适用对象：成员已经在用一个**能执行命令的 AI 编程工具**（ZCode / Claude Code / Qoder /
Cursor / Codex 等）——对目标人群来说这几乎是必然：安装的终点就是把团队技能投递进这些
工具，所以「先有工具、再装 ejdrone」的顺序问题在这个通道里天然不存在。成员的 AI 工具
不能执行命令（纯聊天 App）时，退回 `member-zero-install.md` 的脚本通道。

## 为什么值得多一个通道

| 对比项 | PowerShell 脚本 | AI 委托 |
|---|---|---|
| 成员要会什么 | 复制一条命令进 PowerShell | 复制一段话进自己在用的 AI 工具 |
| 角色选择 | 管理员按群烤 `-Role`，或成员答 CLI 的选择题 | 成员用一句话说职责，AI 对照 `roles list` 的中文说明推荐、成员确认 |
| 出错时 | 报错 + 截图找管理员 | AI 当场读错误原文自行处置（重装 Node、补令牌、重试），搞不定才升级 |
| 平台 | Windows x64 | Windows / macOS / Linux 都能走（B 线） |

## 它是怎么工作的（管理员需要知道的）

1. 成员把 `scripts/install/ai-agent-setup.md`（委托书）粘给自己的 AI，附一句角色职责。
2. AI 盘点环境后有两条线：
   - **A 线（Windows，优先）**：直接运行你托管的 `ejdrone-setup.ps1`。脚本的护栏
     （便携 Node、独立 npmrc、令牌读回校验、首跑/升级判定）全部复用，AI 只负责驱动
     与善后——**不在委托书里重造这些轮子**。
   - **B 线**：无脚本或 macOS/Linux 时手动 `npm install` + `init`，macOS/Linux 成员
     唯一可用的形态。
3. 角色不进命令行：init 走无角色路径，AI 再跑 `ejdrone roles list` 把「id + 说明」
   （来自 `manifest/roles.yaml` 的 description）摆给成员确认，`roles set` + `pull` 落地。
   管理员把角色 description 写清楚，这个通道的角色准确率就高。
4. 验收以 `ejdrone doctor` 全绿为完成标准，AI 用大白话向成员转述。

## 管理员准备

与脚本通道共用同一套准备（见 `member-zero-install.md` §1-§4：仓库可见性决策、制品库
凭据、脚本托管/烤参）。本通道额外只有两件事：

1. **委托书烤参**：改 `scripts/install/ai-agent-setup.md` 顶部「仓库信息」两个地址为
   你的团队仓/源码仓（分发版随脚本一起托管，成员拿到的就是一份完整的）。
2. **description 检查**：`manifest/roles.yaml` 里每个角色都写了人话描述——AI 的角色
   推荐与成员的自助确认全靠它。

## 成员话术模板

> 「我的角色职责」改成你的岗位（比如：产品经理）。「安装脚本位置」一栏用我发你的地址。

## 安全边界

- 委托书内容是静态文本，不含任何令牌；令牌仍只存在于托管的 PS1 脚本（或成员向 AI
  口头提供 `EJDRONE_CODEUP_TOKEN` 时，AI 按委托书写入用户环境变量且不回显）。
- 委托书与脚本同源分发（同一托管位置/同一附件包），完整性要求与脚本一致——成员拿到
  被篡改的委托书等于让 AI 执行攻击者的指令，分发通道要同样可信。
- 委托书明确约束 AI：只做用户级安装、不用管理员权限、令牌不回显、失败先展示原文。
  这些约束靠 AI 遵守，属软边界——敏感环境仍以脚本通道为准（硬边界在脚本里）。

## 已知边界

- 依赖 AI 工具的命令执行能力与指令遵循度：不同工具的执行细节有差异，委托书的步骤
  已按「探测 → 确认 → 执行 → 验证」写成工具无关形态，但无法逐工具穷举验证；成员
  遇到 AI 理解跑偏时，退回脚本通道永远可行。
- AI 推荐的角色仍需成员确认（委托书明确要求），不替成员拍板。
